    The selected policy is:
    
    | Evidence | Upgraded-node behavior |
    |---|---|
    | Frame, phase or samples advance | Continue; reset inactivity tracking |
    | Blender consumes CPU/GPU or performs I/O | Continue; distinguish activity from actual progress |
    | No activity for 5 minutes | Show an inactivity warning |
    | All required measurements confirm inactivity for 15 minutes | Recheck locally, then cancel and retry |
    | Measurements unavailable or stale | Show uncertainty; do not automatically cancel |
    | Render runs longer than historical averages | Continue while activity remains |
    
    There is **no total-duration ceiling** for upgraded nodes. Resource activity cannot prove useful progress, so a spinning or repeatedly logging hang may require manual intervention.
    
    ## Node monitoring and recovery
    
    - Sample Blender and its tracked child processes every **5 seconds**, independently of stdout processing and network sends. Use monotonic elapsed time; evidence gaps exceeding **30 seconds** invalidate continuous inactivity.
    - Collect process identity/aliveness, CPU-time deltas, I/O deltas, memory for diagnostics, and process-specific Windows GPU Engine counters. Track PID plus process creation time to avoid PID reuse. Windows exposes process I/O accounting and GPU accounting covering CUDA/OpenGL, subject to driver support. [Process I/O](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getprocessiocounters), [GPU accounting](https://devblogs.microsoft.com/directx/gpus-in-the-task-manager/)

    - Replace the upgraded server’s stdout-only watchdog with one shared, testable health evaluator. Exclude result delivery and parked continuation from render inactivity checks.

    - Persist configurable warning/inactivity durations globally and per node. Snapshot the effective policy for each attempt; disabling the watchdog disables automatic inactivity cancellation. Upgraded nodes use the same conservative local defaults when no policy is negotiated.
