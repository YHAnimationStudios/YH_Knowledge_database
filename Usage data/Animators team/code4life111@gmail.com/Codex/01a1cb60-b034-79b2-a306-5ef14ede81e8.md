    **Replacing footage while keeping tasks**
    
    There is already a dedicated Replace operation precisely because **delete → insert does not reliably preserve task extents**.
    
    - **Position replacement:** preserves task offsets within the replaced clip. Equal-length replacement preserves timing; a shorter replacement can shorten tasks or leave them orphaned.
    - **Footage-match replacement:** maps tasks onto matching source content. Unmatched portions can become orphaned.
    - **Different replacement length:** shifts subsequent footage and its attached work by the length difference.
    - Locks and task collisions can refuse the operation.
    
    These rules are implemented in [replaceAnimaticClip](E:/YH_Tools/YHAP/packages/planner-domain/src/commands.ts:2744).
    
    For replacing **part** of an existing clip, today’s workflow is: cut at both boundaries → arm replacement footage → choose **Replace with armed clip** on the middle section. However, those cuts can also split scenes/shots, so this is not a purely visual edit.
    
    There are also documented preservation gaps: lifted tasks can shrink and do not automatically regrow when new footage arrives; orphaned tasks can silently adopt footage placed underneath them; ripple handling for orphaned scenes/shots remains unresolved. See [NL1–NL5](E:/YH_Tools/YHAP/Master_development_plan.md:2665).
    
    **What needs defining in your adjusted request**
    
    “Keep tasks intact” could mean several materially different behaviors:
    
    1. **Replace picture at fixed timing:** task IDs, assignments, start/end frames and scene/shot structure all stay unchanged.
    2. **Tasks follow replacement content:** matching or positional mapping may move or resize them.
    3. **Delete picture but retain work:** tasks survive as explicitly unlinked work, even when all picture is gone.
    
    Your existing [Animatic stack plan](</E:/YH_Tools/YHAP/Feature plans/Animatic stack plan.md:107>) already specifies free overwrite across lanes and retaining work as stray when its carrier disappears, but its banner says **nothing built**.
    
    For the workflow you describe, the key distinction is **replacing a selected picture range while preserving task timing and structure**, alongside removing the last-clip deletion restriction. Those are separate changes; simply enabling Delete would not provide safe replacement.

## Assistant (started 2026-11-11T16:39:05.143Z)

    **Your concern is justified. We have a timeline clock, but its settings and duration are still partly owned by the uploaded animatic.** The problem is divided authority rather than a missing timecode counter.
    
    What the code does today:
    
    | Concern | Current authority |
    |---|---|
    | Stored task/scene positions | Integer timeline frames, independent of source-file timecodes |
    | Frame zero | Timeline frame `0`; clips map their source frames onto it |
    | Project FPS | Stored on the project, but `activeFps()` **prefers the active animatic’s FPS** |
    | Displayed timecode | Timeline frame + project `timecodeOffsetFrames`, formatted at `activeFps()` |
    | Timeline ruler length | Maximum of picture, episodes, scenes, tasks and sound—with a 240-frame minimum |
    | Playback length | **Active animatic’s `frameCount`** |
    | Edited animatic length | Recalculated from the primary picture track, with a one-frame minimum |
    | Flat rendition | Uses the active version’s output settings and picture edit |
    
    Sources: [FPS authority](E:/YH_Tools/YHAP/packages/planner-domain/src/model.ts:2710), [timecode conversion](E:/YH_Tools/YHAP/packages/planner-domain/src/time.ts:49), [ruler extent](E:/YH_Tools/YHAP/apps/web/components/planner/Timeline.tsx:1031), [playback configuration](E:/YH_Tools/YHAP/apps/web/components/planner/AnimaticViewport.tsx:522).
    
    **The concrete weakness:** the ruler can show tasks or sound beyond the picture’s end, while playback is bounded by the shorter animatic. Removing picture therefore reaches beyond editing: it changes the object supplying playback duration.
    
    There are already useful foundations:
    
    - Playback uses a **synthetic master clock**; media follows timeline time. It does not require a video element to keep time.
    - Source frames and timeline frames are mapped separately.
    - Gaps already resolve to black.
    - Project FPS exists, and mismatched uploads have a conforming path.
    
    We should build on those rather than introduce dummy clips or preserve an arbitrary minimum video length.
    
    **Recommended architecture**
    
    Give the **project sequence** its own identity and timing settings, separate from uploaded media:
    
    | Project sequence owns | Media source owns |
    |---|---|
    | Timeline FPS | Original/probed source FPS |
    | Starting display timecode | Source timecode, if available |
    | Programme start/end | Source frame count |
    | Picture/audio track placements | File identity and technical metadata |
    | Stable timeline coordinates | Source in/out ranges |
    
    Then distinguish three different lengths:
    
    - **Programme range:** the intended playback/export interval, retained when picture is deleted.
    - **Content bounds:** where picture, sound and planning work currently exist.
    - **Visible workspace:** the ruler’s navigable area, which may extend beyond the programme.
    
    These should have shared domain resolvers. The ruler, transport and exporters can use different ranges deliberately, but should not invent them independently.
    
    Under that model, deleting the last picture clip leaves an empty picture track within an intact sequence. Tasks stay at their existing frames; playback shows black. Uploading a replacement adds a source and placement—it cannot redefine the project’s clock.
    
    For existing projects, migration must capture the **currently effective FPS and timing** before changing authority. Simply switching `activeFps()` to prefer `doc.fps` could reinterpret older projects whose stored rates disagree.
    
    **I recommend making this the foundation of the Animatic stack work**, before replacement and last-clip deletion. The earlier plan’s “retained planning extent” proposal is insufficient by itself: deriving length from tasks would still make the programme shrink when tasks are removed.
    
    The main design choice is how programme end grows: I recommend **automatic extension when placing content beyond it, with shortening only by an explicit action**. Picture deletion should never shorten it implicitly.
    
    This was a source audit; no code or plans changed in this turn.
